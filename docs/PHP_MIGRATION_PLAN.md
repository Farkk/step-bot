# Перенос серверной части на PHP

Статус: локальная реализация Laravel и MySQL собрана и проверена; VPS пока обслуживает Go-версию. React-клиенты остаются в `web/miniapp` и `web/admin`. Целевой сервер — Laravel на виртуальном хостинге Beget с MySQL и cron, без обязательного VPS или Docker.

## Цель и граница совместимости

PHP должен обслуживать те же `/api/v1/*`, `/integrations/max/webhook`, `/health/*`, `/app/` и `/admin/`. Для React сохраняются URL, методы, JSON-поля, коды ошибок, cookie `step_admin`, заголовки `X-CSRF-Token` и `X-Max-Init-Data`. Проверки прав и переходов состояний остаются на сервере. PHP-обработчик MAX должен проверять секрет webhook и подписи запуска, сохранять входящие события до ответа и доставлять исходящие сообщения через очередь.

## Инвентаризация текущей реализации

| Область | Текущий код | Что переносится |
| --- | --- | --- |
| HTTP и конфигурация | `cmd/server`, `internal/httpserver`, `internal/config` | Маршруты, SPA fallback, readiness и настройки окружения |
| Сотрудники и сессии | `internal/admin` | Вход, выход, CSRF, роли, команда, каталог исполнителей, создание первого владельца |
| Исполнители | `internal/profile`, `internal/max/launch.go` | Профиль и проверка данных запуска/контакта MAX |
| Заявки | `internal/tasks` | Создание, публикация, отклики, назначение, статусы, поля, события, рейтинг, аналитика, уведомления и вложения |
| Бот MAX | `internal/max`, `internal/tasks/max_inbox.go` | Webhook inbox, callback, команда `/tasks`, отправка сообщений/фото и outbox |
| Хранение | `internal/storage`, `migrations/001`–`006` | MySQL-миграции и приватное файловое хранилище Laravel |
| Сборка | `Dockerfile`, `compose.yaml`, `compose.vps.yaml` | Локальный PHP/MySQL-запуск, React build и пакет для Beget с публичной директорией `public` |

## Порядок работ

1. Зафиксировать выбор СУБД, PHP-стека и правило сохранения данных VPS.
2. Создать контрактные тесты существующих API и основных сценариев MAX, сначала запустить их против Go-версии.
3. Реализовать Laravel HTTP-слой, конфигурацию, MySQL-миграции, проверки безопасности и базовые маршруты.
4. Перенести операции с заявками, сотрудниками, файлами, аналитикой и репутацией; проверять ответы с теми же контрактами React.
5. Перенести inbox/outbox MAX. Запускать короткую обработку через `php artisan schedule:run` раз в минуту из Beget CronTab; проверить повторные события, callback и ошибки доставки. Не требовать постоянно запущенного worker.
6. Собрать локальное PHP/MySQL-окружение с неизменными React-сборками. Прогнать тесты, сценарий от входа заказчика до завершения и оценки заказа, проверить `/health/ready`, `/app/`, `/admin/`.
7. Обновить `TECH_SPEC.md`, `README.md`, `.env.example`, project skill и `docs/PROJECT_GUIDE.md` по факту работающего PHP-кода.
8. После локальной проверки подготовить пакет для Beget: `public_html` должен указывать на Laravel `public`, PHP для сайта и cron должен быть 8.3+, `.env` и исходники вне web root, HTTPS и MySQL должны быть настроены. Переключать домен/MAX только после проверки основных сценариев на хостинге.

## Решения пользователя

- СУБД: MySQL. Существующие PostgreSQL-миграции не подходят; нужна новая схема с теми же бизнес-ограничениями и транзакциями.
- Сохранение данных и аккаунтов VPS: не требуется. Переносится функциональность, новая MySQL-база начинается пустой.
- PHP-стек: Laravel. Целевое размещение — виртуальный хостинг Beget с cron; Docker нужен только для локального запуска, если он удобен.

## Ограничение обычного хостинга

Cron запускается с точностью до минуты, поэтому фоновые сообщения MAX могут отправляться с задержкой до следующего запуска. Webhook сохраняет событие до ответа; callback отклика обрабатывается сразу, фото подтверждается сразу и отправляется из очереди. Текущий VPS остаётся на Go до проверки на реальном Beget и переключения MAX. PHP-обработчик ограничен 30 сообщениями каждого типа и 40 секундами за запуск; неудачные сообщения остаются в базе и повторяются с растущей задержкой.
